# Sign-in relay and /connect (card #206)

Status: relay and box built and tested with fakes; the Worker bundles. Not live: the relay is not deployed and its `/callback` is not yet registered on the Google and Microsoft apps.

Relay (`src/connect/relay.ts`, packaged as a Worker in `deploy/connect-relay/`, at connect.gethavn.ai): `GET /start` shows a page naming the assistant (the box's registered label) with a warning not to go on with a link someone else sent. Only its button (a same-origin POST, from a page that refuses framing) mints the signed single-use 10-minute state and redirects with a PKCE challenge, so a link forwarded from another box cannot skip the page; `GET /callback` verifies and spends the state, exchanges the code with the matching verifier, and POSTs the result to the registered https origin of that box, signed with that box's hand-off key. The verifier is derived from the signing secret, box and nonce, so nothing is kept between the two steps. A Durable Object holds the used-state keys (so a link works once across every copy of the Worker) and the box registry. No token is stored; the log records the fact of a hand-off only. Deploy and box registration: `deploy/connect-relay/README.md`.

Client secrets: Google's lives only in the relay's Worker secrets. Microsoft needs none: the Havn app is a public client, the relay's callback is registered under "Mobile and desktop applications", and PKCE binds the code to the sign-in.

Box (`src/connect/box.ts`): `/connect gmail|outlook` issues a nonce and a link. The hand-off is accepted only with a valid signature, for a nonce this box issued, once, within 10 minutes, for the same provider. Nonces live in memory, so a restart voids links in flight. `/connect remove gmail` revokes the grant through the relay's `/revoke`, then deletes locally (`--local-only` if the relay cannot be reached). `/connect remove outlook [account]` deletes locally and says where to withdraw access at Microsoft: Microsoft has no call that ends one app's grant for a personal account, and `revokeSignInSessions` needs a permission Havn does not request (and signs the person out everywhere). Yahoo and iCloud point to `/secret`.

Box config (vault or env): `CONNECT_RELAY_URL` (https), `CONNECT_BOX_ID`, `CONNECT_HANDOFF_KEY` (the key the relay minted at registration). Read once at start, so set them and restart.

Where tokens land:

- **Outlook:** the Microsoft token store (`MS_TOKENS_<account>`, `src/ms/store.ts`), the same entry a device-code sign-in writes. The Outlook tools, `ms-auth status` and the web Connections page use it as is, and the box refreshes it with the public client id.
- **Gmail:** `CONNECT_GMAIL`. The refresh token in it is sealed by the relay to this box (AES-GCM, box and provider as associated data): it cannot be renewed by another box or used outside the relay. A refresh token from the relay's Google Web client can only be renewed with that client's secret, which stays on the relay. So the relay renews it (decided 2026-11-01): `GmailTokenKeeper` (`src/connect/gmail-token.ts`) checks every 5 minutes and, once under 30 minutes are left, posts the refresh token to the relay's `POST /refresh`, signed with the box's hand-off key, and gets a fresh access token back. It keeps that token in the service's `GOG_ACCESS_TOKEN`, which every gog call inherits (the agent's Bash, email alerts, the proactive calendar scan) and which gog uses in place of its own stored sign-ins. Email alerts, the proactive calendar and the web Connections page also list the account, since `gog auth list` does not know it.

  What that means in practice:
  - **The relay is a dependency for Gmail.** If it is unreachable, the box keeps the current token until it expires (at least 30 minutes after renewal first fails), then Gmail stops until the relay is back. Outlook does not depend on the relay after sign-in.
  - **A connected relay account takes over gog.** While its token is live, gog calls use it whatever `--account` they name. Discovery (email alerts, proactive calendar, web Connections) then lists that account only, so nothing is filed under an older gog account's name; a box should still not mix the two.
  - **The agent can see the access token.** It is in the service environment, so the agent's Bash can read it, as it can already read gog's keyring password. It lasts an hour and the refresh token behind it is sealed, so a leak is bounded to that hour.
  - **When Google withdraws access** (revoked, password change), the relay answers `invalid_grant`; the box drops the token, keeps the entry (so `/connect list` still shows it), and tells the owner once to run `/connect gmail` again.
  - A turn longer than 30 minutes can outlive the token it started with.
