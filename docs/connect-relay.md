# Sign-in relay and /connect (card #206)

Status: relay and box built and tested with fakes; the Worker bundles. Not live: the relay is not deployed and its `/callback` is not yet registered on the Google and Microsoft apps.

Relay (`src/connect/relay.ts`, packaged as a Worker in `deploy/connect-relay/`, at connect.gethavn.ai): `GET /start` shows a page naming the assistant (the box's registered label) with a warning not to go on with a link someone else sent. Only its button (a same-origin POST, from a page that refuses framing) mints the signed single-use 10-minute state and redirects with a PKCE challenge. The button also sets a ten-minute `__Host-` cookie and the state carries its hash, and `/callback` refuses a state whose cookie is not in the returning browser. So a provider link minted by a script (which can fake the button's headers) fails in anyone else's browser: whoever signs in has seen the page. Checked in Chrome and WebKit over HTTPS with the provider on another site, 2026-11-01; `GET /callback` verifies and spends the state, exchanges the code with the matching verifier, and POSTs the result to the registered https origin of that box, signed with that box's hand-off key. The verifier is derived from the signing secret, box and nonce, so nothing is kept between the two steps. A Durable Object holds the used-state keys (so a link works once across every copy of the Worker) and the box registry. No token is stored; the log records the fact of a hand-off only. Deploy and box registration: `deploy/connect-relay/README.md`.

Client secrets: Google's lives only in the relay's Worker secrets. Microsoft needs none: the Havn app is a public client, the relay's callback is registered under "Mobile and desktop applications", and PKCE binds the code to the sign-in.

Box (`src/connect/box.ts`): `/connect gmail|outlook` issues a nonce and a link. The hand-off is accepted only with a valid signature, for a nonce this box issued, once, within 10 minutes, for the same provider. Nonces live in memory, so a restart voids links in flight. `/connect gmail` can be run once per Google account: each sign-in adds an account, and signing in again with the same address replaces it. `/connect remove gmail <account>` revokes that account's grant through the relay's `/revoke`, then deletes it locally (`--local-only` if the relay cannot be reached); the account can be left off when only one is connected. `/connect remove outlook [account]` deletes locally and says where to withdraw access at Microsoft: Microsoft has no call that ends one app's grant for a personal account, and `revokeSignInSessions` needs a permission Havn does not request (and signs the person out everywhere). Yahoo and iCloud point to `/secret`.

Box config (vault or env): `CONNECT_RELAY_URL` (https), `CONNECT_BOX_ID`, `CONNECT_HANDOFF_KEY` (the key the relay minted at registration). Read once at start, so set them and restart.

Where tokens land:

- **Outlook:** the Microsoft token store (`MS_TOKENS_<account>`, `src/ms/store.ts`), the same entry a device-code sign-in writes. The Outlook tools, `ms-auth status` and the web Connections page use it as is, and the box refreshes it with the public client id.
- **Gmail:** `CONNECT_GMAIL`. The refresh token in it is sealed by the relay to this box (AES-GCM, box and provider as associated data): it cannot be renewed by another box or used outside the relay. A refresh token from the relay's Google Web client can only be renewed with that client's secret, which stays on the relay. So the relay renews it (decided 2026-11-01): `GmailTokenKeeper` (`src/connect/gmail-token.ts`) checks every 5 minutes and, once under 30 minutes are left, posts the refresh token to the relay's `POST /refresh`, signed with the box's hand-off key, and gets a fresh access token back. Since 1.65.0 (card #271) `CONNECT_GMAIL` holds one entry per account (`{"accounts": {...}}`; the #206 single-account shape is still read and rewritten on the next change), and each account renews on its own. A withdrawn grant marks only that account (`/connect list` shows it as needing a new sign-in) and the others carry on.

gog takes one access token, `GOG_ACCESS_TOKEN`, and then uses it whatever `--account` a call names. So the keeper puts the live tokens in `GOG_RELAY_TOKENS` (`{account: token}`), which every gog call inherits, and a gog wrapper (`src/connect/gog-shim.ts`) sets `GOG_ACCESS_TOKEN` per call:

- `--account`, its hidden alias `--acct`, `-a` or `GOG_ACCOUNT` naming a relay account: that account's token. Any other flag starting `--acc` counts as naming an account the box does not hold, so it never falls through to a relay token.
- Naming any other account: no token, so gog uses its own stored sign-in. Accounts signed in with `gog auth add` keep working beside relay ones.
- Naming none: the relay account if it is the only one and gog has no sign-ins of its own. With several, or when `gog auth list` fails so the wrapper cannot tell, it exits 2 with a message asking for `--account` rather than guess.
- `gog auth list` also prints the relay accounts (client `havn-connect`), so the agent sees every account it can reach.

The wrapper is generated at startup into `store/connect-bin/gog` (node shebang, the real gog path baked in, resolved with the wrapper's own directory skipped, so it can never call itself even with `GOG_BIN=gog`). Its directory goes first on the service's `PATH`, which the agent's shell inherits, and `resolveGogBin` returns it for the box's own calls (email alerts, the proactive calendar and threads, support mail, the Connections page). It is only installed when `/connect` is configured, and not on Windows: there, a box with exactly one relay account falls back to that token in `GOG_ACCESS_TOKEN` for every call, as in 1.64. Email alerts, the proactive calendar and the web Connections page list the relay accounts beside gog's own.

  What that means in practice:
  - **The relay is a dependency for Gmail.** If it is unreachable, the box keeps the current token until it expires (at least 30 minutes after renewal first fails), then Gmail stops until the relay is back. Outlook does not depend on the relay after sign-in.
  - **A connected relay account takes over gog.** While its token is live, gog calls use it whatever `--account` they name. Discovery (email alerts, proactive calendar, web Connections) then lists that account only, so nothing is filed under an older gog account's name; a box should still not mix the two.
  - **The agent can see the access token.** It is in the service environment, so the agent's Bash can read it, as it can already read gog's keyring password. It lasts an hour and the refresh token behind it is sealed, so a leak is bounded to that hour.
  - **When Google withdraws access** (revoked, password change), the relay answers `invalid_grant`; the box drops the token, keeps the entry (so `/connect list` still shows it), and tells the owner once to run `/connect gmail` again.
  - A turn longer than 30 minutes can outlive the token it started with.
